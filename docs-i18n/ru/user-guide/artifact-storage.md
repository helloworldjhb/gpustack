# Хранилище артефактов { #artifact-storage }

GPUStack хранит крупные приватные JSON-артефакты в S3-совместимом бакете. Этот слой
используется для архивов мониторинга бенчмарков; браузерные клиенты никогда не получают
учётные данные хранилища. Резервные копии метаданных PostgreSQL/MySQL и объектного
хранилища необходимо создавать согласованно.

## Режимы { #modes }

- `builtin`: упакованный Linux-контейнер запускает **SeaweedFS 4.54** на том же узле.
  Это режим по умолчанию для сервера из контейнерного пакета. Сохраняйте весь том данных
  GPUStack (по умолчанию `/var/lib/gpustack`), включая `artifacts/builtin`.
- `external`: используется общая служба S3 и существующий бакет. GPUStack не создаёт
  бакет и не меняет его политику, шифрование, жизненный цикл или публичный доступ.
- `disabled`: запись новых артефактов прекращается. Явно сохранённые профили чтения
  остаются доступны для чтения. Это режим по умолчанию для установок из исходного кода
  или wheel-пакета, а также для воркеров.

В развёртывании с несколькими серверами необходимо выбрать `external` и использовать
общие бакет и пространство имён. Упакованная служба для одного узла не обеспечивает
репликацию хранилища или гарантии высокой доступности. Учётные данные случайным образом
генерируются один раз, сохраняются в файлах с ограниченным доступом на постоянном томе
и повторно используются после перезапуска. Её конечные точки S3 и внутренние конечные
точки привязаны к петлевому интерфейсу; публиковать дополнительный порт контейнера не требуется.

## Настройка { #configuration }

Настраивайте сервер через YAML-файл, переменные окружения `GPUSTACK_` или флаги CLI
(например, `--artifact-storage-mode external`). В ключах YAML используются подчёркивания,
во флагах — дефисы, а в именах переменных окружения — прописные буквы и подчёркивания.

```yaml
artifact_storage_mode: external
artifact_storage_profile_id: monitoring-eu-v1
artifact_storage_endpoint: https://s3.example.com # omit for AWS endpoint discovery
artifact_storage_bucket: gpustack-private
artifact_storage_prefix: installations/production
artifact_storage_region: eu-west-1
artifact_storage_addressing_style: path # auto, path, virtual
artifact_storage_tls_verify: true
# artifact_storage_ca_file: /etc/ssl/private/s3-ca.pem
```

Если учётные данные не заданы явно, используется стандартная цепочка поставщиков
учётных данных AWS в SDK. Поддерживаются учётные данные из окружения, общая
конфигурация AWS, а также поддерживаемые SDK учётные данные экземпляра, контейнера
или веб-идентичности. Работу конкретных цепочек облачной идентификации необходимо
проверять в целевом развёртывании. Для явного задания учётных данных используются
`artifact_storage_access_key_id`, `artifact_storage_secret_access_key` и необязательный
`artifact_storage_session_token`. Передавайте их через защищённую конфигурацию или
внедрение секретов в окружение. Они исключаются из дампов и строкового представления
GPUStack Config. Не помещайте учётные данные в URL конечной точки.

Проверка TLS включена по умолчанию, в том числе для пользовательских конечных точек.
Задайте собственный центр сертификации с помощью `artifact_storage_ca_file`. Для
отключения проверки сертификатов необходимо явно указать
`artifact_storage_tls_verify: false` или флаг `--no-artifact-storage-tls-verify`.

| Настройка | По умолчанию | Назначение |
| --- | --- | --- |
| `artifact_storage_connect_timeout` | 5 секунд | Тайм-аут подключения SDK |
| `artifact_storage_read_timeout` | 30 секунд | Тайм-аут чтения SDK |
| `artifact_storage_max_attempts` | 3 | Общее число попыток SDK, включая первую |
| `artifact_storage_max_connections` | 8 | Размер пула подключений SDK |
| `artifact_storage_max_concurrency` | 4 | Число одновременно выполняемых вызовов на профиль и цикл событий сервера |
| `artifact_storage_max_object_bytes` | 16777216 | Максимальный размер одного документа в байтах после декодирования |
| `artifact_storage_max_total_bytes` | 0 (без ограничений) | Начальная ёмкость сжатых объектов для всей установки; однократно инициализирует общую политику в базе данных |
| `artifact_storage_builtin_port` | 18333 | Порт S3 на петлевом интерфейсе в режиме builtin |
| `benchmark_archive_retention_days` | Не задано | Следовать сроку хранения бенчмарка; необязательный срок хранения архива в днях |
| `benchmark_archive_sample_step_seconds` | 15 | Шаг сетки выборки сборщика архива |
| `benchmark_archive_flush_interval_seconds` | 60 | Интервал сброса данных архива в хранилище |
| `benchmark_archive_settle_seconds` | 30 | Время ожидания стабилизации исходных метрик |
| `benchmark_archive_max_concurrency` | 2 | Лимит одновременно выполняемых заданий архивации |
| `benchmark_archive_max_run_bytes` | 268435456 | Максимальный размер архива в байтах на один запуск |

Настройки срока хранения и сборщика применяются подсистемой архивов бенчмарков;
адаптер S3 никогда не обрезает слишком большой объект без уведомления. Согласуйте
срок хранения самого бакета со сроком хранения в приложении, чтобы правила
жизненного цикла бакета не удаляли объекты, которые ещё присутствуют в индексе.

## Имена объектов мониторинга { #monitoring-object-names }

В именах новых объектов мониторинга перед неизменяемым UUID указывается область данных:

```text
resources-<uuid>.json.gz
runtime-aggregate-<uuid>.json.gz
runtime-prefill-instances-<uuid>.json.gz
phase-1024-1-runtime-decode-instances-<uuid>.json.gz
```

Каталог уже определяет установку, владельца, бенчмарк, запуск и формат мониторинга,
поэтому имена файлов не повторяют эти поля. Префикс указывает данные времени выполнения
или ресурсов, конкретные роли и представление: агрегированное или по экземплярам.
Для записанных фаз добавляется идентификатор фазы; в файлах полного запуска `run`
опускается. Роль по умолчанию `all` также опускается, как и агрегированное представление
по умолчанию для области ресурсов. Один файл содержит несколько метрик. Компоненты
нормализуются в ASCII-метки ограниченной длины; область, заданная в базе данных,
остаётся определяющей. UUID не позволяет разным сеансам сбора перезаписывать друг друга.

Существующие имена, состоящие только из UUID, не меняются и остаются доступны для
чтения. Чтение, миграция и очистка используют полный ключ объекта из индекса;
пути никогда не восстанавливаются по UUID. Имя файла не определяет активную ревизию
и не гарантирует полноту выборки. Эти свойства по-прежнему хранятся в общем индексе архивов.

## Читаемые манифесты ревизий { #readable-revision-manifests }

После завершения архива в состоянии `ready`, `partial` или `no_data` отдельный
фоновый цикл создаёт манифест для каждой опубликованной ревизии:

```text
installations/<installation>/owners/<owner>/benchmarks/<id>/runs/<run>/
  monitoring/v1/manifests/revision-000001.json
```

Это обычные несжатые JSON-файлы в UTF-8 с отступами, поэтому их можно просматривать
в браузере S3 или Filer. Кривые мониторинга остаются отдельными gzip-объектами.
Для ранее завершённых архивов манифесты создаются по опубликованным индексам из базы
данных, без запросов к Prometheus и без изменения данных мониторинга. Активные сеансы
сбора ожидают завершения архива; необязательная запись манифестов не блокирует
продолжающийся цикл сбора.

Каждый документ указывает свою неизменяемую ревизию и перечисляет области, фазы,
роли, представления, имена и единицы измерения метрик, покрытие выборки, ключи объектов,
размеры и значения SHA-256. Поддерживаемые метрики содержат подробные метаданные;
`unavailable_metrics` компактно группирует неподдерживаемые и неприменимые ключи
с указанием причин. Поддерживаемые метрики без отсчётов выделяются отдельно.
Временные значения сохраняются в секундах Unix и дополняются читаемыми отметками
времени UTC. `revision_state` описывает сохранённую ревизию, а не текущее состояние
задания. В манифест не копируются исходные промпты, учётные данные, команды запуска,
переменные окружения или приватные адреса источников.

Значения `stored_bytes` фиксируются при первой подготовке манифеста. При последующей
миграции профиля может использоваться другое gzip-кодирование с сохранением данных.
Для объектов кривых `checksum_scope: uncompressed_json_bytes` означает, что SHA-256
рассчитывается по декодированным байтам JSON, а не по загруженному файлу `.json.gz`.
Для самого манифеста контрольная сумма охватывает его фактические байты JSON в UTF-8.

База данных определяет активную ревизию и факт фиксации её манифеста; изменяемого
указателя `latest.json` нет. Загрузка может завершиться до сбоя подтверждения в базе
данных, поэтому само наличие файла не доказывает, что ссылка на манифест зафиксирована.
Обычный ответ на аутентифицированный запрос
`GET /v2/benchmarks/<id>/monitoring-archive` содержит объект `manifest`:

```json
{
  "state": "ready",
  "archive_revision": 1,
  "filename": "revision-000001.json",
  "size_bytes": 12345,
  "sha256": "<sha256>",
  "checksum_scope": "utf8_json_bytes"
}
```

Это же поле может сообщать `pending`, `failed` с безопасным описанием `last_error`
или `unavailable`. Оно не раскрывает приватную конфигурацию бакета или профиля либо
полные ключи объектов. Ошибка создания манифеста, включая отказ из-за нехватки ёмкости,
не меняет состояние сбора и не делает уже сохранённые графики недействительными;
фоновые повторные попытки могут завершить его создание позднее.

Манифесты используют общий реестр учёта байтов и участвуют в миграции профилей,
аудите целостности, удалении бенчмарков и удалении архивов по истечении срока хранения.
Они не расходуют лимит байтов мониторинга на один запуск. При неизвестном результате
загрузки сохраняются проиндексированное намерение записи и резерв ёмкости;
их состояние согласуется при успешной повторной попытке. Фиксированные ключи
манифестов исключены из обычной очистки бесхозных объектов и очистки для освобождения
ёмкости, чтобы устаревший процесс очистки не удалил повторно публикуемый объект;
явное удаление архива или истечение срока хранения по-прежнему удаляет их все.
Отклонённая загрузка, которая не была начата, не оставляет бесхозного объекта.

## Общая ёмкость { #global-capacity }

Ёмкость применяется ко всей установке GPUStack, ко всем серверам и настроенным
профилям хранилища. Учитываются сжатые байты управляемых объектов, включая сохраняемые
ревизии архивов, неопубликованные объекты и обе копии при миграции профиля. Также
учитывается место, зарезервированное для записей, результат которых в S3 ещё не
подтверждён. Не учитываются другие файлы в бакете, издержки репликации объектного
хранилища, сохраняемые версии объектов S3 и место файловой системы, которое
SeaweedFS ещё не освободила.

По умолчанию ёмкость **не ограничена**. Задайте `artifact_storage_max_total_bytes`
в YAML, `GPUSTACK_ARTIFACT_STORAGE_MAX_TOTAL_BYTES` в окружении или
`--artifact-storage-max-total-bytes` при запуске сервера, чтобы установить начальную
политику при первой инициализации. Значения задаются целым числом байтов; `0` означает
отсутствие ограничений. Максимальный поддерживаемый настраиваемый лимит составляет
`9007199254740991` байт. Все серверы должны использовать одинаковую начальную
конфигурацию. После инициализации определяющей становится общая политика в базе
данных: перезапуск сервера с другим начальным значением не перезаписывает политику,
сохранённую администратором.

Администраторы платформы могут просматривать или менять действующую политику без
перезапуска серверов через `GET` / `PUT /v2/artifact-storage/capacity`; PUT принимает
`{"max_bytes": 0}` для снятия ограничений либо положительный лимит в байтах. Ответ
содержит `used_bytes`, `reserved_bytes`, `total_bytes`, `remaining_bytes`,
`usage_percent` и `state`. В режиме без ограничений оставшиеся байты и процент
использования возвращаются как null. В режиме с ограничением при 80% выдаётся
предупреждение, а при достижении или превышении лимита состояние становится `full`.

CLI предоставляет доступ к той же общей политике:

```sh
gpustack artifact-storage --config-file /etc/gpustack/config.yaml capacity
gpustack artifact-storage --config-file /etc/gpustack/config.yaml \
  capacity --max-bytes 107374182400
gpustack artifact-storage --config-file /etc/gpustack/config.yaml \
  capacity --max-bytes 0
```

Резервирование ёмкости выполняется последовательно в общей базе данных до загрузки.
Запись, для которой недостаточно места, возвращает `storage_capacity_exceeded`;
она не может незаметно вытеснить историю или обрезать архив. Существующие архивы
остаются доступны для чтения, а выполнение запросов бенчмарка и сбор клиентской
статистики продолжаются независимо. Увеличение лимита, снятие ограничений или удаление
управляемых архивов может позволить возобновить ожидающий сбор. Пропущенный интервал
исходных данных можно восстановить только пока Prometheus ещё хранит эти данные.
Допускается снижение лимита ниже текущего использования; это блокирует выделение
дополнительной ёмкости, но не удаляет существующие данные.

Место освобождается только после подтверждения удаления со стороны S3. Неудачные
или прерванные загрузки консервативно сохраняют резерв до тех пор, пока согласование
или очистка не подтвердят результат. Существующие объекты добавляются в реестр при
первом использовании; для устаревших объектов с записанным намерением загрузки или
копий миграции с неизвестным сжатым размером используется консервативный резерв
на основе их несжатого размера. Из-за этого отображаемый объём выделенного места
может временно превышать фактический размер сохранённых данных. Этот механизм
не сканирует использование всего бакета и не управляет политикой жизненного цикла
S3. Версионирование бакета, блокировка объектов и освобождение физического дискового
пространства остаются ответственностью администратора хранилища.

## Состояние сбора и покрытие исходных данных { #capture-status-and-source-coverage }

`capture_complete` описывает зафиксированную для чтения ревизию архива. Для ревизий
`ready` и `no_data` значение равно true, а для ревизии `partial` с ошибками сбора,
идентификаторами, утратившими действительность, или недоступными измеряемыми областями
— false. `archive_state` сообщает текущее состояние задания, которое может меняться,
пока клиент продолжает читать более раннюю ревизию.

`data_coverage` отдельно описывает сохранённые наблюдения источника. Короткая фаза
может иметь состояние `ready` с `capture_complete: true` и `data_coverage: partial`,
если первый такт выборки предшествует первому сбору метрик или её скользящее окно
задержки слишком короткое. При этих условиях сохраняются статусы метрик, значения
null, нулевые значения и статистика покрытия; повторять успешный сбор не требуется.
Сбои запросов остаются ошибками сбора, допускающими повторную попытку. Успешная
повторная попытка публикует новую ревизию и сохраняет предыдущую для читателей,
зафиксировавших её.

## Профили хранилища и их изменение { #storage-profiles-and-changes }

Идентификатор профиля навсегда определяет конечную точку, бакет, префикс и регион.
Адаптер сохраняет привязку по отпечатку в `artifacts/profiles` и не позволяет
повторно использовать этот идентификатор для другого назначения. Индексы архивов
также сохраняют идентификатор профиля. Ротация учётных данных для того же назначения
не требует нового идентификатора.

При смене назначения выберите новый идентификатор профиля записи и сохраните старое
подключение в `artifact_storage_read_profiles`. Записи профилей используют те же
настройки без префикса `artifact_storage_`. Задайте это сопоставление через YAML
или переменную окружения `GPUSTACK_ARTIFACT_STORAGE_READ_PROFILES` в формате JSON.

```yaml
artifact_storage_profile_id: monitoring-eu-v2
artifact_storage_bucket: new-private-bucket
artifact_storage_read_profiles:
  monitoring-eu-v1:
    endpoint: https://old-s3.example.com
    bucket: gpustack-private
    prefix: installations/production
    region: eu-west-1
    addressing_style: path
    # Credentials may be omitted to use the SDK credential chain.
```

Обеспечьте доступность старых профилей и их объектов, пока все зависимые архивы не
будут перенесены или удалены. Переключение в режим external или disabled останавливает
упакованную службу SeaweedFS; сначала перенесите локальные объекты либо оставьте
отдельно доступную службу для чтения старых данных. Простое копирование файлов в
новый бакет не переписывает индексы архивов. Никогда не удаляйте привязки профилей
только ради того, чтобы изменённое назначение прошло проверки.

## Необходимые операции S3 { #required-s3-operations }

Адаптер использует SigV4 `HeadObject`, `PutObject`, `GetObject` и `DeleteObject`.
Предоставляйте среде выполнения доступ только к настроенному пространству имён.
При наличии поддержки используется условный `PutObject` с `If-None-Match: *`.
`artifact_storage_conditional_writes: false` явно выбирает переносимый режим S3;
адаптер также переходит в этот режим при явном ответе о неподдерживаемом условии.
Ошибки прав доступа и конфликты параллельных операций никогда не вызывают такой
переход. Переносимые операции записи проверяют существующее содержимое, но не могут
сделать HEAD и PUT атомарными: вызывающий код должен использовать уникальные ключи
объектов и публикацию с защитой от устаревшего владельца через базу данных, как это
делает архиватор бенчмарков. При идентичных повторных попытках проверяется сохранённая
контрольная сумма. ETag — непрозрачные значения, которые никогда не трактуются
как контрольные суммы MD5.

Проверка подключения только для чтения использует `HeadBucket`, для которого в AWS
требуется `s3:ListBucket`. Поэтому отказ при проверке может указывать на отсутствие
разрешения для проверки работоспособности, даже если операции с объектами разрешены.
Проверка никогда не создаёт бакет и не меняет данные. Только инициализация встроенного
режима использует `CreateBucket` для управляемого им бакета.

Каждый документ независимо сжимается gzip и содержит SHA-256 канонического несжатого
JSON в UTF-8. При чтении проверяются сохранённые метаданные и ожидаемая контрольная
сумма из индекса, ограничивается число как сжатых, так и декодированных байтов,
а поток ответа закрывается. Все операции ввода-вывода SDK и сжатие выполняются
вне цикла событий. Ошибки возвращают стабильные безопасные причины без содержимого
исключений SDK или учётных данных.

Флаги подключения к хранилищу, переменные окружения и настройки YAML описаны
в [справочнике конфигурации CLI](../cli-reference/start.md#artifact-storage-options).
Внешний режим подключается к существующей S3-совместимой службе; GPUStack не
развёртывает её реплики, не управляет ими, её базой метаданных или доступностью.

Упакованная служба использует HTTP-порты 18333 (S3), 19333 (master), 18080 (volume),
18888 (filer) и внутренние gRPC-порты 29333, 28080, 28888. Все они привязаны к
петлевому интерфейсу. Настраивается только порт S3. Данные master, данные объектов,
LevelDB компонента Filer и учётные данные находятся внутри `artifacts/builtin`;
резервной копии части тома недостаточно.

## Область проверки { #verification-scope }

Модульные тесты выполняются без сети и охватывают ограничения размера в байтах,
контрольные суммы, неизменяемость при повторных попытках и конкурирующие записи,
безопасные ошибки, конфигурацию, сохранение учётных данных, отключённый режим,
профили чтения и вынос операций SDK из цикла событий. Локальный дымовой тест
SeaweedFS 4.54 проверяет загрузку в S3, скачивание, сохранность после перезапуска,
проверку контрольных сумм и удаление. Сборки Linux-образов для обеих архитектур,
а также сценарии идентификации AWS и других поставщиков, TLS, прав доступа,
производительности и сбоев требуют проверки на уровне развёртывания.

Флаги и контрольные суммы закреплённой версии бинарного файла соответствуют
[официальному выпуску 4.54](https://github.com/seaweedfs/seaweedfs/releases/tag/4.54),
[команде server](https://github.com/seaweedfs/seaweedfs/blob/4.54/weed/command/server.go)
и [документации по настройке S3](https://github.com/seaweedfs/seaweedfs/wiki/Amazon-S3-API).

## Миграция профилей и аудит целостности { #profile-migration-and-integrity-audit }

Административный CLI напрямую использует настроенное подключение к базе данных.
Он открывает существующую схему; не создаёт таблицы, не выполняет миграции,
не инициализирует поставщиков аутентификации и не запускает службы хранилища.
Перед запуском настройте исходный и целевой профили. Поддерживайте согласованную
резервную копию базы данных и объектов.

Просмотрите план для выбранного запуска без загрузок и изменений базы данных:

```sh
gpustack artifact-storage --config-file /etc/gpustack/config.yaml \
  migrate-profile --source-id monitoring-eu-v1 --target-id monitoring-eu-v2 \
  --benchmark-id 7 --run-id RUN_UUID --dry-run --manifest /secure/migration-plan.json
```

Примените ту же выборку с `--apply`. Если опустить оба флага действия, также выполняется
пробный запуск. `--archive-id`, `--benchmark-id` и `--run-id` позволяют сузить выборку;
`--limit` ограничивает один вызов (по умолчанию 100, максимум 1000 архивов). Команда
обрабатывает только архивы в состояниях `ready`, `partial` или `no_data` и отказывается
захватывать архив с действующей арендой. Она не восстанавливает данные из Prometheus
и не переносит незавершённые сеансы сбора или сеансы, завершившиеся с ошибкой.

Для каждого архива миграция получает существующую аренду в базе данных, увеличивает
её токен защиты от устаревшего владельца и до загрузки сохраняет предполагаемые
ссылки на исходные и целевые объекты. Она повторно использует стабильные ключи
объектов в целевом профиле, проверяет SHA-256 источника и назначения, сохраняет
прогресс по каждому объекту и после успешной проверки всех объектов меняет
идентификаторы профиля архива и его опубликованных фрагментов в одной транзакции
с проверкой токена защиты. Идентификаторы областей, ревизии архивов, отметки времени
и контрольные суммы содержимого остаются неизменными. Поэтому опубликованные
ревизии воспроизводят те же данные. Изменения разных архивов фиксируются независимо;
даже пакет, завершившийся с ошибкой, может уже содержать успешно перенесённые архивы.

После прерывания повторно выполните ту же команду. Завершённые архивы больше не
соответствуют исходному профилю, а незавершённые копии продолжаются с надёжно
сохранённого прогресса. Потеря аренды блокирует публикацию; другой процесс может
продолжить работу после истечения аренды (до трёх минут). Отсутствующая целевая
копия создаётся заново из проверенного источника; повреждённая или конфликтующая
копия останавливает миграцию для расследования администратором. Исходные копии
остаются нетронутыми на всём протяжении процесса, в том числе после успешной миграции.

Сохраняемые исходные и незавершённые целевые копии остаются проиндексированными
в истории миграции архива. При обычном удалении бенчмарка или по истечении настроенного
срока хранения архива они очищаются тем же заданием сборки мусора с повторными
попытками. Сохраняйте их профили хранилища в конфигурации до завершения очистки.
Неявного немедленного удаления исходных копий или команды очистки всего бакета нет.
Предусмотрите временную ёмкость для дублирующихся данных.

Проверьте текущие проиндексированные объекты, не меняя хранилище или строки базы данных:

```sh
gpustack artifact-storage --config-file /etc/gpustack/config.yaml \
  audit --profile-id monitoring-eu-v2 --manifest /secure/integrity-report.json
```

`check` — псевдоним `audit`. Применяются те же фильтры по архиву, запуску и бенчмарку,
а также тот же лимит. Отчёт выявляет отсутствующие объекты, несовпадения контрольных
сумм, недоступные профили и безопасные причины сбоев хранилища; он не содержит
данных объектов или учётных данных. Код завершения — 0 при успехе, 2 при обнаружении
проблем аудитом и 1 при ошибке операции. Если указан `--manifest`, отчёты записываются
с правами доступа только для владельца. Аудит проверяет опубликованные объекты из
индекса, не сканируя весь бакет и не пытаясь угадать, какие неучтённые объекты можно удалить.
